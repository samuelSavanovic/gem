# Optimization TODOs

Future performance improvements. None are blocking — collect ideas here as they come up. Shipped optimizations live in [`OPTIMIZATIONS_LOG.md`](OPTIMIZATIONS_LOG.md) with their work logs and benchmark anchors.

Priorities come from the yardstick programs in `examples/` (`bookmark_app`, `stomp_broker`, `logstat`, `mini_redis`, `lox`, `gemgrep`, `jobqueue`) and their harnesses in `benchmarks/`.

Priority scale: **P0** = measurable impact on benchmark right now, **P1** = significant but requires groundwork, **P2** = nice to have or niche.

## Current performance reference

The bookmark app, on one scheduler thread, serves `/` (static HTML) at 90k req/s against 65k for its Node twin, and `/bookmarks` (a sqlite query rendered to HTML) at 11k against 17k (`benchmarks/run.sh` and `benchmarks/node_baseline/run_bench.sh`, wrk with 10 connections on the same machine, macOS arm64, `benchmarks/baselines/2026-10-07_m1pro`). Recorded benchmark runs are in `benchmarks/baselines/`, and shipped optimizations with their before and after numbers in `OPTIMIZATIONS_LOG.md`.

Text processing in one process runs a little faster than Python: `examples/logstat` summarizes 1M access-log lines (123 MB) in 1.29–1.38 s, from stdin or from a file, against 1.67–1.71 s for the same program in Python (`benchmarks/logstat/run.sh`, macOS arm64, `benchmarks/baselines/2026-10-07_m1pro`; `--by hour` is the fast end). Resets take little of it, since they promote the aggregate tables instead of copying them again (OPTIMIZATIONS_LOG.md, "Promote what a reset keeps"): with `GEM_DIAG=1 benchmarks/logstat/run.sh` they take 0.05–0.10 s of each run, copying at most 10 MB (macOS arm64, October 2026); in a `sample` profile (`--by ip`, from a file) the rest is spread over string-key hashing in table get/set ("Hash string table keys faster"), `substr` copies, std/string's argument checks and the per-call overhead of Gem code. Memory stays flat on stdin (the arena resets keep up); a file is held whole, twice at the peak.

The CPU-bound core runs faster than CPython: `examples/lox`, a tree-walking interpreter, takes 0.41–0.64 times the time of the same interpreter in Python on its six bench programs (`benchmarks/lox/run.sh`, macOS arm64, `benchmarks/baselines/2026-10-07_m1pro`). Nearly all of its field reads miss their inline cache ("Inline caches key on the table, not its shape"), and 1–14% of its time is system time, faulting in fresh arena pages ("Resets unmap the blocks they free"). A recursion frees what its calls allocate as they return: Lox `fib(28)` peaks at 10 MB on macOS arm64, Python at 20 MB (`benchmarks/baselines/2026-10-07_m1pro`; OPTIMIZATIONS_LOG.md, "Free a recursion's garbage at function return"), and the return points cost the interpreter 2–3% of its instructions (5% on `binary_trees`; `fib` runs 2% fewer) ("A return point costs about 20 instructions a call").

C interop is cheap per call and the code around it is not: `examples/gemgrep`, a recursive grep calling libc's `regexec` once per line through a plain `extern fn`, takes 1.4–17 times GNU grep's time and 0.56–2.6 times a Python twin's (`benchmarks/gemgrep/run.sh`, macOS arm64, `benchmarks/baselines/2026-10-07_m1pro`). Most of that is libc's `regexec` itself: `benchmarks/gemgrep/regexec_floor.c`, which reads each file, finds its lines with `memchr` and calls `rx_exec` from `examples/gemgrep/rx.h` on each, takes 8.86 G of the 9.95 G instructions of `gemgrep -rc error` on a 64 MB corpus (`benchmarks/gemgrep/gen_corpus.py <dir> 64`; 6.08 G of 7.16 G for `-rn deadbeef`; macOS arm64, October 2026), so the Gem code around the calls (the line walk, the binding's argument checks; "Small Gem functions cost 200–300 instructions a call") costs about 830 instructions a line (1.08 G over 1.3 million lines, in both). In those two cases (`count` and `few` in the baseline) the floor alone takes more instructions than the whole Python twin, whose `re` is faster than macOS's `regexec`. An `extern blocking fn` is no way out for short calls ("An `extern blocking fn` call costs a thread hand-off").

Failure handling costs little; big state in one process does. `examples/jobqueue`, a job queue whose pool workers crash, hang and get killed under a `dynamic_supervisor`, runs its six fault scenarios at 0.90–2.5 times the throughput of the same design in Python asyncio and 1.0–1.3 times Elixir's (also with Elixir held to one scheduler), with the same invariants holding in all three (`benchmarks/jobqueue/run.sh`, macOS arm64, `benchmarks/baselines/2026-10-07_m1pro`). What it shows is memory and pauses: `backlog` (100,000 jobs) peaks at 390 MB, against 173 MB for Python and 237 MB for Elixir, and only the queue loop's full resets copy its whole state: the longest reset there takes 0.08–0.09 s, and every process waits for it ("Full resets still copy all a loop keeps").

Key bottlenecks under the current arena + region-reset mechanism:
- Per-process arena allocation eliminates GC pauses; every loop resets the region it allocated once it passes max(1 MB, 2 × the last reset's cost), promotes what the reset kept, and runs a full reset once the kept memory has doubled (or grown fourfold, after a full reset that found little garbage), so memory is bounded at a small multiple of a loop's live data plus whatever was allocated before the loop started. A function that can recurse also resets what its call allocated when it returns, once that passes 1 MB, so a recursion's memory follows its depth, not its number of calls.
- String concatenation patterns that escape `build_string` still allocate per-concat.
- Every loop entry takes a region mark and every back-edge checks the trigger (a load and a compare); every call of a function that can recurse records a return point (about 20 instructions) and compares at its return; the reset itself is amortized O(1) per allocated byte (see `OPTIMIZATIONS_LOG.md` "Region resets").

## Arena / Memory

### A loop's first reset is full, so short loops nested in a recursion copy the same data at every level (P1)
Promotion (OPTIMIZATIONS_LOG.md, "Promote what a reset keeps") stops a loop from copying its own survivors again, but a fresh mark's first reset is always full, and a recursion that runs a short loop at every level gets a fresh mark per level. `examples/lox`'s `binary_trees.lox 12` builds each tree through `init`, whose body runs in the interpreter's `for s in statements` loop: `this.left = Tree(depth - 1)` builds a whole subtree in one iteration, the loop's back-edge resets with that subtree live (stored in the older instance, so the remembered-log walk copies it), and the enclosing level's statement loop then copies the same subtree again as part of its own. Every node is so copied once per level above it: 5,125 resets, 3,286 of them full, copy 1.36 GB, 1.8 s (0.96 s of it the walk) of an 8.2 s run, and without the program's one long-lived tree the numbers barely move (1.31 GB), so this, not the long-lived tree, is the cost (GEM_DIAG=1, Linux x86_64 VM). Short loops nested in other loops pay the same first full reset: in `gemgrep -rn e`, 655 of 1,693 resets are full, and the resets copy 1.6 GB (2.1 GB before promotion), 1.0 s of a 4.9 s run. Options: a loop whose mark is newer than the mark of an enclosing loop of the same function could start out promoted (treat its first reset as young, with the enclosing loop's young point as its base); or skip a reset whose region holds one large young object graph rooted only in an older table, leaving it to the enclosing loop, which would copy it once.

### A kept table written once is walked whole at every reset (P1)
Promotion makes a loop's big tables older than its young point, so a write to one logs it in the remembered log, and the next reset walks every entry of it to fix up the ones pointing at young memory. `examples/jobqueue`'s queue writes its job table at every message, so each of its resets scans all 100,000 entries in the `backlog` scenario: the resets scan 485 MB (`scanned=`) against 76 MB before promotion, still cheaper than the copying they replaced, and the walk is half of the queue's reset time (0.96 s of 1.94 s). `examples/mini_redis` under the soak load (`GEM_DIAG=2 TARGETS=mini_redis DURATION=5m benchmarks/soak/run.sh`, about 10,000 commands/s, macOS arm64; the figures here are from two such runs, whose logs are not committed) pays it on every request: the store's gen_server loop resets about every 0.3 s, and each young reset frees about 5 MB and copies about 350 KB, but walks the whole `db.data` table (about 73,000 entries) and scans about 8 MB in all, taking 4–13 ms, 60% of it the walk (2.97 s of the 4.80 s its young resets took in 5 minutes). Resets as a whole take 8% of the server's CPU time (8.0 s of 94.8 s). Writes to a table like `db.data` land at scattered positions, so neither the lowest index written nor 64-entry cards would help much there: about 2,500 commands run between two resets, about 40% of them writes in this load's mix (`benchmarks/soak/mini_redis_load.py`), which dirty more than half of its 1,150 cards. Logging the written slot itself would make the walk proportional to the writes: the barrier takes the index (`gem_table_set` calls it before it knows the slot); `delete` and `remove_at`, which move entries without calling the barrier, log the slots they move entries into; and a table whose slot log passes a fraction of its length, or that `insert` or `sort` shifts, falls back to the whole-table walk.

### Full resets still copy all a loop keeps, in one pause (P1)
A full reset copies everything the loop keeps, and it comes once the kept memory has doubled since the last one. A loop whose kept data turns over (records replaced, keys deleted) needs them to give the garbage back, so they come regularly, and one that finds most of the kept data live pushes the next one out to fourfold growth. In `examples/jobqueue`'s `backlog` scenario 32 of about 910 resets are full, and the longest one takes 0.08–0.09 s (`max=` in the GEM_DIAG line; macOS arm64, `benchmarks/baselines/2026-10-07_m1pro`); at 20,000 jobs the longest is 0.09 s, and `jobqueue --jobs 20000 --slow 0.1` still kills 0–5 healthy attempts per run for overrunning their 100 ms deadline (8–16 before promotion). A loop whose kept data only grows pays for promotion too: a process that keeps one record per message copies 316 MB at 300,000 records, against 214 MB when every reset copied everything, because each record is copied when it is promoted and again by each full reset (its peak RSS is 288 MB against 381 MB, and its longest reset 0.25 s). A loop that replaces a big state wholesale peaks higher, since each replaced state stays kept until the next full reset: a 50,000-record list rebuilt at every iteration peaks at 264 MB, against 152 MB before promotion, in the same time. In `examples/mini_redis`'s store under the soak load, a full reset comes about every 20 s and copies the 22–31 MB the store keeps in 25–55 ms (the same 5-minute runs), and no command runs meanwhile; over the 8-hour soak run the longest reset was 0.53 s (`benchmarks/soak/results/2026-10-08_m1pro_8h`, on a Mac busy with other work: `max=` is wall-clock time), and 0.09 s in an hour on a Linux VM (`benchmarks/soak/results/2026-10-07_linux-vm`), against a p99 command latency of 1.8 ms. Options: age objects (promote only what survived two young resets, so short-lived records die young and full resets come less often), or make the full reset incremental (copy the kept area in slices between iterations, with the barrier tracking writes to the part already copied).

### A loop keeps its high-water memory after its live data shrinks (P2)
The next reset of a loop waits until the loop has allocated at least 1 MB and twice what the last reset copied plus half what it scanned (after a full reset, half what it scanned), so a loop that held a lot and then dropped it keeps that memory until it allocates as much again, and an idle one keeps it for good. `examples/mini_redis` after 1M SETs with a 2 s TTL (632,000 distinct keys), on macOS arm64: 865 MB RSS after the fill and 866 MB 9 s later, with 163,000 of its 632,000 keys left (Redis: 61 MB, none left; `benchmarks/baselines/2026-10-07_m1pro`); 134 MB of it is freed large malloc blocks that macOS's allocator keeps resident ("Resets malloc and free their large temporaries at every reset"). Options: let the budget decay with time, or have the scheduler run a pending reset when a process with a large region blocks in `receive` (the cost is then off the request path).

### Resets malloc and free their large temporaries at every reset (P2)
A reset's copy map (`GemCopyMap` in `runtime/gem_copy.c`) keeps its hash table in malloc once it outgrows a 16-entry inline buffer: it starts at 64 entries, doubles as the reset copies (each grow frees the old table), and is freed when the reset ends; the pin sweep (`gem_pin_sweep_from`) deletes the boxes it frees from the pin set's stb_ds hash map, which shrinks it. A reset that copies a big region so mallocs and frees blocks of several MB each time. In `examples/mini_redis`'s 1M-key TTL fill on macOS arm64, resets free 220 MB in blocks of 1 MB or more (an interposed `free`), and macOS's malloc keeps freed large blocks resident: after the fill, `vmmap -summary` shows 134 MB of "Malloc Large (empty)" in an 864 MB RSS (a separate run of the same fill), and the same run with `MallocLargeCache=0` ends at 729 MB. Fix: keep the copy map's table and worklist per arena between resets, cleared rather than freed and sized to the last reset's, and keep the pin set from shrinking during a sweep, so the large blocks are allocated once.

### Resets unmap the blocks they free, and the next allocations fault fresh pages (P1)
A region reset `munmap`s the region's blocks (`gem_arena_free_blocks`), and the loop's next iterations `mmap` new ones, so every byte a loop allocates is a fresh zero page again: one page fault per 4 KB. In `examples/lox` the Gem runs spend 20–30% of their time in the kernel: `closures.lox 100000` frees 2 GB in 1,388 resets and takes 525,000 minor faults, 1.0 s of system time in a 4.5 s run (Python: 99,000 faults, 0.4 s); `binary_trees.lox 12` frees 7.4 GB, 1.1M faults, 1.6 s of 7.3 s; `fib.lox 28` 0.9 s of 3.1 s. Fix: keep the blocks a reset frees on a per-arena free list, up to about the loop's reset budget, and hand them out before mapping new ones; unmap the rest (and the list when the process exits or the loop ends), so memory still comes back when a loop's live data shrinks.

### A return point costs about 20 instructions a call (P2)
A function that can recurse records a `GemArenaPoint` at entry (`gem_arena_point`: the arena's current block and offset, its table and buffer list heads, the pin sequence, a clock bump, the allocated-minus-freed count) so its return can reset (OPTIMIZATIONS_LOG.md, "Free a recursion's garbage at function return"). That is about 20 instructions a call, against 200–300 for the call itself. Given to every function that calls something, it cost logstat 6.5% of its instructions, `examples/jobqueue` 4–5% and `examples/lox` 4–6% (macOS arm64), so only functions on a cycle of the call graph get one (`mark_recursive_fns` in compiler/callgraph.gem): logstat +0.2–0.5%, gemgrep +0–0.3%, lox +2–3% (its interpreter core is all recursive; `binary_trees` +5%). The rule for indirect calls is coarse (one reaches every closure and every named function used as a value), so `examples/jobqueue`, whose only recursion is the std supervisors' self-tail-call loops, still gives its gen_server callbacks and the queue functions they call points: +1–3%. What that leaves out: a non-recursive call that allocates a lot and returns something small keeps its garbage until an enclosing loop or recursive call resets or the process exits. A cheaper point would let every function have one. One option: stamp blocks, tables and buffers with the `bytes_allocated` count at their creation, make a point just that count and the clock, and have the reset recover the block offset and list heads from the stamps (a reset's copies reuse the free tail of an older block, which such stamps would have to allow for).

### Return resets copy a large live return value whole (P2)
A return reset copies everything its call returns that the call allocated, and the next one waits for twice that copy (four times, when the reset found the region mostly live) plus half what it scanned. A recursion that returns big live structures pays the copy and holds both copies for its duration: the compiler's self-compile (`build/gem compiler/main.gem --emit-c`), whose parser returns ASTs up its levels, makes 81 return resets copying 56 MB and peaks at 118 MB against 105 MB without them (+3% instructions); `lox binary_trees.lox 12` makes 803 copying 319 MB (the subtree an `init` returns, much as in "A loop's first reset is full" above), and its peak falls from 78 to 46 MB all the same. Options: skip a return reset whose region holds little besides the return value (it would need an estimate before copying, such as the bytes allocated since the last nested reset), or promote the copied value so an ancestor's reset leaves it in place.

### Garbage allocated before a loop starts is kept by that loop (P2)
A region reset frees only what the loop allocated since its mark. Garbage from straight-line code before the loop (e.g. main's startup work before a top-level `while true` server loop) stays until an enclosing loop resets or the process exits. It is a constant, not growth. For loops at depth 0 of the main program the mark could sit at the start of the arena (main has no caller frames and its module slots are roots), reclaiming startup garbage too; spawned bodies would need their env rooted.

### Remembered log instead of a per-table walk for buffers (P2)
Region resets find old tables written since the mark through a write barrier and a remembered log, but still walk every buffer older than the mark (cost charged to the hysteresis budget). A barrier in `buf_push`/`gem_string_append_to` growth would make the walk proportional to the buffers actually grown.

### Mailbox messages are copied by the resets that find them in the region (P2)
Messages are deep-copied into the receiver's arena by the sender, so a backlog that arrives during a loop is part of that loop's region: a reset copies it once and promotes it, and full resets copy what is still queued again, until it is consumed. Every reset still walks the whole mailbox (relinking nodes a selective receive unlinked), so each queued message is charged 256 bytes to the reset budget, which spaces the resets out as a backlog grows; skipping the part of the mailbox older than the young point would need the relinking done another way. Hysteresis keeps the total linear (300 × 100 KB messages drain in linear time), but a large backlog doubles its memory while a reset runs, and consumed messages stay in the kept memory until the next full reset. Allocating message bodies in a separate per-process message arena that a reset never scans (freed when the message is received and dropped) would avoid both; the cost is a second allocator and a copy (or ownership transfer) when the message is received.

## Value Representation

### NaN boxing (P1)
GemVal is currently 24 bytes (4-byte type enum, 4-byte magic, and a 16-byte union whose largest members are a string's pointer and length and a closure's function and env pointers). NaN boxing packs type + value into a single 8-byte double by exploiting the NaN payload space. Cuts memory per value to a third, improves cache locality, eliminates the type field branch in hot paths. The payoff isn't just memory — every function call, table lookup, and arithmetic op passes GemVals, so halving their size compounds across the entire runtime. Requires rewriting every GemVal constructor and accessor. Major undertaking but large payoff. Would also directly reduce arena allocation pressure since every value, table entry, and function argument shrinks.

## Strings

### String views / slices (P1)
`substr` allocates a copy. A view (pointer + offset + length) into the original string would make substring extraction O(1). Strings already carry their length (`slen`), but every consumer that relies on the trailing NUL (C interop, `printf %s`) would need to copy or check views first. Defer until profiling shows substring allocation as a real bottleneck — the C interop boundary assumes null-terminated strings throughout, and `substr`/`ord(s, i)` already cover the hot cases without changing the representation.

### `find_any` and a byte-mapping builtin, so the remaining std string loops run in C (P2)
A byte loop written in Gem (`ord(s, i)` per byte, plus a reduction check and a reset check at every back-edge) costs about 50 ns a byte, against about 1 ns in C. `find` covers searching for a fixed needle (OPTIMIZATIONS_LOG.md, "`find` builtin"); two kinds of scan still run in Gem:

- `find_any(s, chars, start)` — index of the first byte at or after `start` that is in the set `chars`, or -1. `html_escape`, `url.encode` (1 MB with a reserved byte every 10: 215 ms, Linux x86_64), `url.parse_query` and tokenizers like the `std/json` scanner scan to the next special byte, then copy the whole run before it. `trim` needs the inverse (skip bytes that *are* in the set, like `strspn`), so give it a negate flag or a sibling `skip_any`. std/http and std/request reach the span case today through the runtime extern `gem_bytes_span`; a builtin would retire it.

`upper`/`lower` copy unchanged runs with `substr` but still allocate a string per changed byte (`add(chr(c))`): `string.upper` of 1 MB of mostly lowercase text takes 160 ms, `lower` of the same text 80 ms. They need a byte-mapping builtin rather than either of these.

### String interning for short strings (P1)
Small strings (< 16 bytes) could be interned in a global table, turning equality checks into pointer comparison. Most table keys are short identifier strings — this would speed up every `gem_table_get`/`gem_table_set` with string keys. Trade-off: interned strings must live in a shared arena or be reference-counted so they outlive individual process arenas. Would also reduce per-process allocation rate for keys built at runtime (literal keys like `"tag"` are already static, `GEM_STR_LIT`).

### `gem_string()` copies unconditionally (P2)
`gem_string(const char *s)` always allocates + memcpy. Callers that already have an arena-allocated string pay for a redundant copy. A `gem_string_own(char *s)` variant that takes ownership would eliminate this.

## Codegen Output

### Don't pin plain local reads for left-to-right evaluation (P2)
Left-to-right evaluation (`left_to_right` / `operands` / `pin_operand` in codegen.gem) copies every operand that isn't a literal or a temp into a C temp when a later operand runs code, plain C locals (`gem_v_s`, `gem_v__for_i_N`) included. On a 50M-iteration `s = s + t[i % 10] * 2 + len(t) - (i % 7)` loop that is +9–10% over the old (wrong-order) code on macOS arm64 (1.78 s vs 1.62 s); removing just the local pins gets back about a third of it. A plain unboxed local can only change mid-expression through a later operand that assigns it, which after "assignment is a statement" means a non-escaping closure assigning it through its stack env (`g(x, pcall x = 2)` must still read the old `x`). So: treat `gem_v_<name>` as inert unless a later operand of the same expression assigns `name` (directly, or in a non-escaping closure's `stack_env_writes`). Boxed locals and module slots stay pinned.

### Large C frames: about 1 KB for a small function, 2 KB with a `match` (P2)
`gcc -O2 -fstack-usage` on `examples/lox` (October 2026): a three-line `check_numbers` takes 576 B of stack, `ancestor` (a `for` loop over `.enclosing`) 736 B, `evaluate` and `execute` (a 12- and a 9-arm `match` on a string) 1,792 and 2,000 B. Each call's arguments go in their own addressable `GemVal _tN[] = {...}` array (24 B per value; 16 of them in `execute`, besides 50 scalar temporaries), and a reset loop adds a `GemArenaMark` (120 B: two arena points and the reset budget). A Lox call recurses through about ten such frames, so the 8 MB process stack holds 600–900 interpreted calls, and the interpreter caps them at 256. Options: one scratch argument array per function, sized for its largest call and reused (arguments are evaluated into temporaries first anyway); direct calls with C parameters for named fns of known arity, which would also skip the `argc` checks.

### Small Gem functions cost 200–300 instructions a call (P2)
In `examples/gemgrep`, the per-line path is a loop that calls `regex.test(rx, data, start, stop)`, which calls `check` (three range comparisons, a `len`, a field read) and then the extern wrapper. In callgrind (`gemgrep -c deadbeef` on a 163,000-line input not in the repository, Linux x86_64 VM, October 2026, at commit 228cb42, when neither function was a leaf and `len` and `ord` went through their `(env, args, argc)` functions) a line cost 2,160 instructions: 1,110 in glibc's `regexec`, 56 in the extern wrapper, and the rest in Gem code: `regex.test`'s own body 254, `check` 214, the loop body 272, `find` 120. `check` is a leaf, and `len` and `ord` have direct entry points (OPTIMIZATIONS_LOG.md, "Leaf functions may call builtins"): on macOS arm64 that took 110–210 instructions a line off `gemgrep -rc`. `regex.test` calls `check`, so it pushes a frame and sets the line before every statement, and its arguments, like every call's to a Gem function or extern, go through a `GemVal` array and the callee's argc checks. Ways down: direct calls with C parameters for named fns and externs of known arity ("Large C frames"), and inlining a small leaf like `check` into its caller.

### `match` on string literals compares bytes arm by arm (P2)
`match e.kind when "literal" ... when "super"` compiles to a chain of `gem_val_eq` calls, each a length check and a `memcmp`, so the twelfth arm costs twelve comparisons. In a callgrind profile of `examples/lox` (`fib.lox 20`), `gem_val_eq` runs 46 times per interpreted call and takes 5% of the instructions, `memcmp` another 2%. Most of these strings are literals on both sides (`GEM_STR_LIT` values point at C string constants, which the C compiler merges), so a pointer-equality check before the `memcmp` would settle most of them; a `match` with only string-literal arms could also switch on the length and first byte, or hash the target once.

### Dead code elimination (P2)
Unreachable code after `return`, `break`, `error()` could be stripped. Currently emitted as-is.

## Runtime Hot Paths

### Inline caches key on the table, not its shape (P1)
Each `t.field` site has a one-slot cache (`GemICacheSlot`, `gem_table_get_cached` in gem.h) that hits only when the *same table* comes back with the same `shape_id`, and every table gets its own `shape_id` when it is created. Code that reads the same field of many tables, such as a tree walk over records (`node.kind`, `node.left`) or objects of one class, misses every time and looks the key up again (`gem_table_get_ic_miss`: a scan of the keys in a table without a string-key index, a hash in one with an index, and a `strlen` of the literal key on each miss). In `examples/lox`, 810,881 of 821,119 cached field reads missed (99%) in `fib.lox 20` (callgrind, October 2026). The log entry that introduced the cache (OPTIMIZATIONS_LOG.md) expected one shape per site in AST walking, but shapes are per table. Fix: hidden classes. Give tables built with the same sequence of string keys the same shape (a transition tree from the empty shape, as V8 and LuaJIT's templates do: `{kind:, op:, left:, right:, line:}` literals from one site always share one), cache `(shape, index)` per site, and change the shape only when a key is added out of order or removed. The miss path should take the key length from codegen instead of `strlen`.

### Tables past 8 entries `calloc` their index, and resets walk every table they drop (P2)
A table with more than `GEM_TABLE_SCAN_MAX` (8) entries and a string key gets its string-key index (`gem_str_index_alloc` in runtime/gem_core.c), `calloc`'d outside the arena, and a region reset walks every table its region allocated to `free` the indexes of the dead ones (`post_tables` in `gem_region_reset_impl`), small tables included, so a reset's cost still grows with the garbage it drops. Allocating the indexes in the arena would let dead ones go with their blocks and remove the walk; an index in a reset's region must then be copied or rebuilt with its table (deep copies already leave it to `gem_table_index` through `index_stale`), and `gem_rekey_index` must allocate a replacement when the older table it fixes up has its index in the region.

### Hash string table keys faster (P1)

The string-key index (`gem_str_index_*` in runtime/gem_core.c) hashes the
key's `slen` bytes with byte-wise FNV-1a on every lookup. Measured on
macOS arm64 with 200k keys: 1M lookups take 95 ms against 84 ms with the
old stb_ds index (about +13%), while insert/delete churn got faster.
Cache the hash on the string (strings are immutable), or use a
word-at-a-time hash. A literal key (`GEM_STR_LIT`) could carry a hash
computed by the compiler. `gem_str_index_get` and `gem_str_index_put`
are the two largest runtime functions in a `sample` profile of logstat
(`--by ip`, October 2026). Tables of up to 8 entries that never grew
past that scan their keys instead (`gem_table_str_pos`); larger ones,
such as Lox's global environment, still hash on every lookup.
rapidhash and wyhash are single-header C word-at-a-time hashes that
could be vendored into runtime/ (like stb_ds.h); the gain is mostly on
keys longer than about 16 bytes.

### String-key table lookups are inlined only by cc's choice (P2)

`gem_table_get`, `gem_table_set` and `gem_table_get_ic_miss` (the field
read path when the inline cache misses) in runtime/gem_core.c find a
string key through `gem_table_str_pos`, an extern function declared in
gem.h and also called from runtime/gem_builtins_collection.c. Apple
clang 21 at `-O2` inlines it into all three, and that is worth 4–5% of
the instructions of `examples/lox`'s six bench programs: with
`__attribute__((noinline))` on it they run 0.5–1.0% fewer instructions
than at commit 31ebd79, where `gem_table_set` called it, and 4.6–6.2%
fewer without it (macOS arm64, `benchmarks/lox/run.sh`, October 2026).
Nothing in the source asks for the inlining, so a change that grows
any of these functions can lose it, and a different compiler may not do
it. Fix: a `static inline` lookup in gem_core.c that the three call,
with the extern `gem_table_str_pos` a wrapper for the other callers.

### Float to string tries up to three `snprintf` + `strtod` rounds (P1)

`gem_format_float` (runtime/gem_core.c) finds the shortest decimal that
reads back as the same double by formatting with `snprintf("%.*e")` at
15, 16 and 17 significant digits and parsing each with `strtod` until
one round-trips. `print` and value formatting (`fmt_value`), `to_string`
and string interpolation (`gem_interp`) all go through it. Ryu (plain C, Apache-2.0 or Boost licensed)
computes the shortest round-trip digits in one pass without libc,
typically 10–30× faster than a `printf`-family call. Its digits and
exponent would feed the existing layout code below the loop unchanged.
The current function gives a check to test against: both must produce
identical output for random doubles, subnormals, powers of ten and the
integer-valued floats. The lox benchmarks (all Lox numbers are floats)
should show it.

### `to_float` parses with `strtod` (P2)

`to_float` (runtime/gem_builtins_core.c) and through it std/json's
number parsing call libc `strtod`, which is slow, especially on macOS.
The Eisel–Lemire algorithm (Lemire's fast_float) parses decimal floats
several times faster with correct rounding, but its reference
implementation is C++, so this needs a C port (an `extern "C"` shim
would make the runtime build need a C++ compiler). The fast path is a
few hundred lines plus a table of 128-bit powers of ten and can fall
back to `strtod` when it can't decide; Wuffs' single-file C release may
already have one to vendor. Worth doing only if a
parse-heavy profile (JSON decoding of numeric data) shows `strtod`.

### `buf_push` specialization for non-strings (P2)
`buf_push` auto-coerces non-string values via `to_string`, allocating a temporary string. Specialized variants (`buf_push_int`, `buf_push_float`) that write directly into the buffer would skip the allocation. Small win per call but high frequency in formatting-heavy code.

### Table grow strategy (P2)
`gem_table_grow` doubles capacity. Could use a growth factor of 1.5 to reduce memory waste, or start with capacity 0 (no allocation) for tables that might stay empty.

## Runtime I/O

### `read_file` holds the file twice at its peak (P2)
The I/O worker reads the file into a malloc'd buffer, and `gem_read_file_fn` (runtime/gem_builtins_io.c) then copies it into the arena: logstat on a 123 MB log peaks at 239–243 MB RSS, against 3–7 MB reading the same lines from stdin (macOS arm64, `benchmarks/baselines/2026-10-07_m1pro`). Allocating the arena block first and having the worker read into it, or adopting the malloc'd buffer as a large arena block, would halve it; a line reader (ROADMAP "Line-at-a-time input") would keep only the current line.

### Selective receive save-queue optimization (P1)
`receive ... when` scans the mailbox from oldest to newest on every wake. If a process accumulates many messages and the match is near the end, that's O(n) pattern matches per wake. Erlang's optimization: remember which messages were already tested against the current receive and skip them on re-scan, only testing newly arrived messages. Non-trivial but maps onto the existing mailbox structure — a "scan cursor" per process that advances as messages are rejected and resets when the receive shape changes or a new message arrives.

The case that hurts in practice is a reply wait in a process whose mailbox holds messages it will read later. `examples/jobqueue`'s driver first submitted its jobs with one `gen_server.call` each from the process that also receives every job's `job_done`: each call's wait for `_gs_reply` scanned all the notifications queued so far, and 10,000 jobs took 21 s instead of 0.7 s. A bare test: 10,000 calls to a server that sends the caller a note per call take 14 s in Gem and 31 ms in Elixir (`+S 1`), against 68 ms in Gem with the calls in a process of their own (Linux x86_64 VM; BEST_PRACTICES.md, "A process that makes calls doesn't also collect a stream"). OTP avoids the scan without the general cursor: a `receive` whose patterns all match a ref created by `make_ref()` just before (the compiler sees `Ref = make_ref(), ..., receive {Ref, _} -> ...`) starts at a mailbox marker set when the ref was made, since no older message can hold it. Gem can do the same at runtime: `make_ref()` records the mailbox tail in the process, and a `receive` whose every arm pins that ref (`ref: ^ref`, as `gen_server.call`, `task.await` and the dynamic supervisor's requests do) starts after it. `DOWN` arms in the same receive (a call that also watches its server) need the monitor set after the marker, which those std functions already do.

### kqueue/epoll for sockets (P2)
The scheduler currently uses `poll()` for socket readiness. Replacing with **kqueue** (macOS/BSD) or **epoll** (Linux) would improve scalability at high connection counts (thousands of fds). `poll()` scans the entire fd set on each call — O(n) per wake. kqueue/epoll return only ready fds — O(ready). For the current HTTP server benchmark (~100 concurrent connections), `poll()` is not the bottleneck; this optimization matters when scaling to thousands of simultaneous connections: the scheduler rebuilds and polls the whole fd-waiter set on every idle wake-up, and while processes run it spaces the polls by twice their cost (at most 1 ms apart), so with a few hundred waiters a busy process can lose up to a third of its time to polling, and socket wake-ups wait up to twice a poll's cost (300 idle sockets beside a CPU-bound process on macOS arm64: 2,000 socket round trips take 1.05 s and the process's work 0.74 s, against 0.64 s and 0.97 s when polling after every pass). kqueue/epoll would make the non-blocking check after a pass O(ready) and remove that trade-off.

## Scheduler / Concurrency

### Fan-out writes one message per syscall (P1)
`examples/mini_redis`'s pub/sub sends each published message to every subscriber's connection process, which writes it to its socket. Redis delivers messages 27× faster to 100 subscribers and 47× faster to 1,000 (7.5M against 282k, and 9.2M against 194k deliveries/s), and Gem is at 0.42× with one subscriber (`benchmarks/mini_redis/run.sh`, phase `pubsub`, macOS arm64, `benchmarks/baselines/2026-10-07_m1pro`). Every delivery is a `write` of its own: 200,121 `write` calls for the 200,000 deliveries to 100 subscribers, 201,003 for 1,000 (`benchmarks/mini_redis/write_count.c` interposed on the server under `pubsub_bench.py`, macOS arm64, October 2026). Redis appends to each client's output buffer and writes it once per event-loop pass, so a burst of 100 PUBLISHes costs each subscriber one write. Here every subscriber runs as soon as the send wakes it, before the next message exists, so the connection's "take every queued message, then write once" loop never finds a second one; and the publishing connection makes one `gen_server.call` per PUBLISH, so subscribers run between any two publishes. Options: in the app, send a pipelined run of PUBLISHes to the pubsub server in one call (as the store's batches do); in the runtime, have `tcp_write` of a small buffer append to a per-socket output buffer that the scheduler flushes once per pass, as Redis does (the write's result then reports what was buffered, and a failure shows on a later write, as it already can).

### Multi-threaded work-stealing scheduler (P2)
The scheduler is single-threaded — one scheduler loop round-robining coroutines on one OS thread. N scheduler threads with per-thread run queues and work-stealing (Chase-Lev deque) would scale throughput ~linearly with cores. The per-process arena model already eliminates shared-heap contention. Hard parts: mailboxes need lock-free MPSC queues for cross-thread sends, shared globals (`gem_proc_table`, `gem_name_registry`, free list) need synchronization, each thread needs its own kqueue/epoll set, and process migration (stealing a coroutine between scheduler ticks) needs care. Erlang/BEAM does exactly this architecture. Nothing in the current design blocks it — isolated processes, message passing, and per-process memory are the right foundation.

### Per-process footprint: four memory mappings and ~21 KB (P1)
Every live process costs about 21 KB of memory on Linux x86_64 (about 70 KB on macOS arm64, whose pages are 16 KB) and four memory mappings: the stack block is three (minicoro's header, the `PROT_NONE` guard, the stack), the arena's first block a fourth. On Linux the per-program mapping limit `vm.max_map_count` (default 65,530) therefore stops `spawn` at about 14,000 live processes (it keeps 1/8 of the limit as headroom for the running processes; "spawn: too many processes for the system's memory-mapping limit"), well below the process table's 262,144. Measured on Linux x86_64: 1,000 idle processes in 23 MB, 10,000 in 210 MB, 50,000 in 1.0 GB, 100,000 in 2.1 GB (with the limit raised); on macOS arm64, 10,000 in 0.68 GB, 50,000 in 3.5 GB. Ways down, roughly in order of payoff: carve the first arena block out of the stack mapping (above the stack top, so a process is three mappings); move `GemProcess.pcall_stack` (64 frames with a `jmp_buf` each, 15 KB of the 22 KB slot) and `call_stack` (256 frames, 6 KB) out of the slot into lazily allocated blocks, so an idle process touches one page of its slot; and allocate stacks from larger mappings carved into guarded slabs (one `mprotect` per guard still splits the mapping, so this needs guard-less stacks with a red-zone check only, or `MAP_GROWSDOWN`-style tricks — weigh against the stack-overflow containment in gem_scheduler.c "Process stacks").

### A module-level table that grows between spawns is copied for every child (P1)
`spawn` puts each module-level binding whose value changed since the last spawn into a new snapshot unit (gem_copy.c, "Module globals"), a malloc'd copy the child keeps until it exits, whether or not it reads the binding. Top-level code that does `push(pids, spawn(...))` in a loop therefore copies `pids` once per spawn, O(n²) in time and memory: 3,000 spawns 290 ms, 6,000 spawns 1.0 s, 10,000 spawns 11 s and 2.6 GB, against 64 ms, 116 ms and 0.2 s with `pids` a local of a function (Linux x86_64). A program that keeps tens of thousands of processes hits it, so it is a trap (BEST_PRACTICES.md, "Don't grow a module-level table while spawning"). Fix options: build the unit lazily, at the child's first read, from a copy-on-write freeze of the parent's table (the parent's next mutation copies instead); or share one unit between consecutive spawns and record only the appended tail per child.

### `monitor` of one target by many processes is O(n²) (P2)
`gem_monitor_fn` walks the target's whole monitor list to deduplicate (and to drop nodes of exited watchers), so n processes monitoring one target cost O(n²): 5,000 in 0.3 s, 20,000 in 6.6 s, 40,000 in 38 s on Linux x86_64; 0.14 s, 1.5 s and 6.4 s on macOS arm64 (spawning the watchers included: 0.05 s, 0.19 s and 0.38 s of it). A per-target hash set of watcher pids (or a per-watcher set of targets checked from the caller's side) makes it O(1); the exited-watcher cleanup can happen when the target dies.

### `cancel_timer` scans the timer heap (P2)
`gem_cancel_timer_builtin` finds the timer by a linear scan of `gem_timers`, so cancelling many of a large number of pending timers is O(timers) each. An index from timer ref to heap position (kept up to date by the sift functions, as the scheduler's deadline heap does with `dl_idx`) makes it O(log n).

### Supervisor restart bookkeeping is O(restarts in window) per restart (P2)
`std/supervisor` (`note_restart`) and `std/dynamic_supervisor` (`check_intensity`) rebuild `state.restart_times` on every restart, keeping the times inside `max_seconds` (at most `max_restarts + 1` of them, since one more crashes the supervisor). A restart therefore costs O(restarts in the window): 8,000 restarts of a permanent child took 394 ms with a 1 ms window and 7.2 s with a 100 s window and a huge `max_restarts`. The times are pushed in order, so a queue that drops expired entries from the front (a head index into the array, compacted now and then) makes each restart amortized O(1). Only matters for supervisors configured to tolerate thousands of restarts per window. `examples/jobqueue` is one: its workers crash with their jobs, so its worker supervisor allows 1,000 restarts a second. 20,000 jobs with a 20% crash rate (4,860 worker restarts) run in 2.6 s with a 1 s window and 3.8 s with a 100 s window (`jobqueue --jobs 20000 --crash 0.2 --retries 10 --max-restarts 1000000 --restart-window 100000`, Linux x86_64 VM).

## C Interop Hardening

### String-return ownership convention is path-dependent (P2)
`extern blocking fn` String returns are documented (SPEC §C Interop) to be `malloc`/`strdup`'d — the runtime copies into the arena and `free`s the original. `extern fn` (non-blocking) String returns are *not* freed: the runtime `gem_string`s the pointer (which copies) but the original is leaked if it was malloc'd, or fine if it was a static literal. Two reasonable behaviors with opposite ownership rules, documented in SPEC ("String-return ownership"). Options for removing the asymmetry: (a) unify on the blocking convention (always free), which is the most consistent but breaks the obvious `getenv`/`strerror`-style use case; (b) introduce a `StringStatic` / `StringOwned` distinction.

### An `extern blocking fn` call costs a thread hand-off (P2)
Each call of an `extern blocking fn` copies its `String` and `Bytes` arguments into malloc'd memory, signals a pool worker through a condition variable, and is woken through the wake pipe and a `poll` of the scheduler, even when the C work takes nanoseconds. Calling glibc's `regexec` on each of 19,000 lines of a 1 MB file took 5 ms as a plain `extern fn`, 0.64 s as an `extern blocking fn` given each line (33 µs a call), and 1.7 s given the whole file with offsets (90 µs a call: the 1 MB copy; Linux x86_64 VM). So a blocking call can't be used for short work in a loop, and `examples/gemgrep` runs its matching inline, which lets one pathological pattern stall every process. Options: skip the copies (the calling process is suspended, so its arena doesn't move during the call; what needs care is a process killed mid-call, whose arena would have to outlive the worker's use of it, as the request already does); spin briefly for the completion before sleeping in `poll` when nothing else is runnable; or an `extern fn` variant that runs inline but lets the scheduler preempt to the pool only past a time budget.

## std/json

### Scanner as plain table instead of closure (P2)
The closure-based scanner (`{peek, advance, skip_ws}`) pays for hashmap lookup + closure call + captured variable access on every character. A flat table `{input, pos, length}` with module-level functions `peek(s)`, `advance(s)`, `skip_ws(s)` avoids closure overhead. More idiomatic for a language without methods.
